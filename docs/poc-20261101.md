# ooRexx on the JVM: WebAssembly (WASI) + Chicory — 01/11/2026

*The proof of concept's report, built in the LLMs chain and imported as
the starting point of this repository. Translated from the Spanish
original; the files it lists are now at the root of the repository.*

A feasibility test asked for by Josep Maria following Rony G.
Flatscher's proposal (e-mail of 01/11/2026): to have ooRexx everywhere
there is Java, Android and z/OS (IBM Semeru) included. Instead of
rewriting the interpreter in Java, **the usual ooRexx C++ interpreter**
is compiled to WebAssembly with WASI and run by **Chicory**, a
WebAssembly runtime written in pure Java (no JNI, no native code), which
also translates the wasm into JVM bytecode.

## Result

**It works.** ooRexx trunk r13289, compiled for `wasm32-wasip1-threads`,
runs on Java 21 on Chicory 1.7.5:

| Test | JVM (Chicory) | Native r13271 |
|---|---|---|
| `hello.rex` (`PARSE VERSION`, decimal arithmetic) | correct; `REXX-ooRexx_5.3.0(MT)_32-bit`, `PARSE SOURCE` = `WASI` | — |
| `conc.rex`: 4 activities with `START`, `GUARD ON WHEN`, `REPLY` | identical to native (counter 4000) | identical |
| `err.rex`: error trapped with `SIGNAL ON SYNTAX`; error in an activity (`hasError`, 42.3) | identical to native | identical |
| `sys.rex`: files, `.Stream`, the queue, `SysFileTree`, `INTERPRET`, `rxregexp`, `DATE`/`TIME`, environment | identical to native | identical |
| `sys.rex`: `address system "echo hi"` | RC 127 (WASI has no processes) | `hi`, RC 0 |
| Rexx Parser, `pbench2.rex` with dump (27 files, 171,372 elements) | **dump byte-for-byte identical to native** | — |
| Rexx Parser, 3 passes (`pbench2.rex 3`) | **216.7 s** | **63.9 s** (3.4 times less) |
| Start-up (`hello.rex`, from scratch) | ~3.6 s (JVM + translating the 2.6 MB wasm) | instant |
| `rexx.img` | generated by `rexximage.wasm` running on Chicory during the build: 6 s | — |

Machine: virtual Xeon at 2.1 GHz, 2 cores, Ubuntu 24.04, OpenJDK 21.0.12.

## How it is done

1. **wasi-sdk 34** (clang 23), target `wasm32-wasip1-threads`: threads
   (wasi-threads, shared memory) and C++ exceptions with WebAssembly's
   standard encoding (`-fwasm-exceptions -mllvm
   -wasm-use-legacy-eh=false`; Chicory does not read the legacy one).
2. **`oorexxwasm`'s base patch** (`patches/0001-wasm-build-and-base-runtime.patch`,
   Josep Maria's, on top of Tom Dyer's port): static librexx, the API
   server (queues, registrations, macrospace) inside the process, native
   packages embedded (no `dlopen`). Applies cleanly to r13289.
3. **A WASI patch on top** (`0001-wasi-on-top-of-oorexxwasm-0001.patch`,
   413 lines): the generic `__EMSCRIPTEN__` branches become `ORX_WASM`
   (Emscripten or WASI); under WASI only `rxregexp` and `rxmath` are
   embedded; `sigaction` and `rusage` set aside; no `SysCSStream.cpp`
   (no sockets).
4. **Compatibility headers** (`compat/`): what wasi-libc lacks (`pwd.h`
   with a single user taken from the environment, `termios.h`, `netdb.h`,
   `spawn.h`, `sys/wait.h`, `sys/ipc.h`, `sys/sem.h`), all failing with
   `ENOSYS`/`ENOTTY` where appropriate; `orx_wasi_compat.h` (included in
   every unit) with `getuid`, `getppid`, `fork`… and `<cstdlib>`/`<exception>`,
   because libc++ is stricter than libstdc++ about `std::abs` and
   `std::exception_ptr`; `orx_wasi_stubs.c` with `fork`, `system` and a
   constructor that does `chdir($PWD)` (WASI always starts in `/`).
5. **The Java launcher** (`host/`, ~100 lines): Chicory's WASI with the
   host file system mounted at `/`, shared memory, and **`thread-spawn`
   written here**: Chicory implements the threads standard (atomics,
   shared memory) but not the WASI function that creates a thread; each
   thread is a Java thread with its own instance over the same memory.
   Chicory's compiler is used (wasm → bytecode at start-up).
6. **`-DORX_ENABLE_IPO=OFF`**: with LTO, the final code generation
   happens in the linker without `-fwasm-exceptions`, and **every**
   `catch` disappears (0 `try_table` in the binary): any Rexx error
   killed the program. Without LTO: 2,473 `try_table` and everything
   correct.

`build.sh` rebuilds it from scratch (tested: 3 minutes on that machine,
downloads aside).

## What is missing or cannot be

- **Commands** (`ADDRESS SYSTEM`, `ADDRESS COMMAND`): WASI preview 1 has
  no processes. They can be provided with a function imported from the
  host that uses Java's `ProcessBuilder`: a few dozen lines on each side.
- **Sockets** (`rxsock`): not in WASI preview 1 either. Same remedy (Java
  has IPv4/IPv6 sockets and TLS), or WASI preview 2 when Chicory has it.
- **Java from Rexx**: the strategic interest for Rony. It would need
  host functions that expose Java reflection (a BSF through the wasm).
  Not done.
- **Signals and HALT** (Ctrl-C): WASI's emulated `signal()` only delivers
  what the program sends itself. The JVM's Ctrl-C would have to reach the
  interpreter through another imported function.
- **32 bits**: wasm32 limits memory to 4 GiB (here, 2 GiB), and
  `PARSE VERSION` says `32-bit`.
- **Start-up**: ~3.6 s because Chicory translates the wasm every time. Its
  build-time compiler (`build-time-compiler`, Maven) would leave it as
  bytecode inside the jar.
- **Not tested** on z/OS or Android: only OpenJDK 21 on Linux. The jar is
  pure Java (Chicory states it has no native dependencies), so in
  principle it runs on Semeru; Android has its own rules for loading
  classes generated on the fly (the build-time compiler would avoid them).
- **Not the official suite**: what was tested is the programs in `tests/`
  and the Parser. The next serious step would be to run ooRexx's test
  suite, as `oorexxwasm` does.

## Compared with the alternative (the RVM in Java)

Josep Maria's RVM (a compiler over the Parser plus a virtual machine,
with hosts in ooRexx and in JavaScript) could have a third host in Java.
This route, instead, is **the same interpreter**: the same semantics,
trunk's fixes arrive by themselves (the WASI patch is small), and it is
3.4 times slower than native, while the RVM in JavaScript is about 100
times slower according to its documentation. The RVM would win in
interoperability with Java (it would be direct) and in readability.

## Files

- `build.sh` — full rebuild.
- `0001-wasi-on-top-of-oorexxwasm-0001.patch` — the WASI patch (on
  trunk r13289 with `oorexxwasm`'s 0001 applied).
- `compat/` — WASI compatibility headers and stubs.
- `wasi-p1-threads.cmake` — wasi-sdk's toolchain with the
  `wasm32-wasip1-threads` triple (wasi-sdk's own uses the old
  `wasm32-wasi-threads`, which does not find the libraries).
- `host/` — the Java launcher (Maven: `mvn package` → `target/rexxjvm-0.1.jar`).
- `tests/` — `hello.rex`, `conc.rex`, `err.rex`, `sys.rex` and `t.cpp`
  (the minimal C++ test with threads and exceptions).
